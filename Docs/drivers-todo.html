Drivers for real hardware

What BeeCodersOs needs before it is usable on a real PC, in the order to build it, with the state of each item.

Target machine: HP EliteDesk 800 G1 (Intel Haswell, Q87 chipset) · started 15 November 2026 · BeeCodersOs 0.0.3

Where we are: on the HP the OS boots from the USB stick (legacy BIOS mode) to its prompt, the keyboard types, the internal SATA disk is found and left untouched, and the network works: the I217-LM gets an address from the router and answers a ping from another machine. It still runs from a RAM disk. Next: decide where BeeFS lives on the HP (D2, D3), so files, settings and crash reports survive a restart.

Why 0.0.2 stopped after the hello line (solved)

The hello line is the first thing the kernel prints; the next line ([mem] ...) never appeared. So the stop is in what runs in between (kernel/src/main.rs):

SuspectWhyLikelihood
Writing to the serial portEvery character also went to COM1, waiting for the port without a limit. The hello line reaches the screen first; the first character for the serial port then waits forever on a port that never reports ready.Highest. Fixed by S1.
Reading the boot arguments, setting up the heapBoth read the bootloader's memory information. A fault here comes before the interrupt table exists, so the machine freezes or resets without a message.Lower. B1 would show it.
The bootloader checkPrints a message when it fails, unless that message was itself stuck in the serial wait.Low.

Confirmed on the machine: 0.0.3 b1, which changes only the serial port code, reaches the prompt.

The list

Tier 0: get past the hello line

The kernel waited on hardware without a time limit. On a PC where that hardware is missing or behaves differently, the boot hangs without a word.

  • S1 Serial port: detect it, never wait forever S

    Every printed character also goes to COM1. The old code waited for the port to be ready with no limit, which is the most likely reason the HP stops right after the hello line. Now the port is detected at start (COM1 and COM2), output to a missing port is skipped, and a port that does not become ready costs one short wait and is then left alone until it works again.

    Code: kernel/src/uart.rs (new, shared), serial.rs, aibridge.rs. Tests: self-test "serial port: missing or stuck hardware never hangs"; a boot in QEMU with -serial none. Shipped in 0.0.3 b1.

  • S2 Serial port: reading never loops forever S

    The interrupt handlers and the start-up emptied the receive buffer in a loop that only ended when the port said "empty". They now stop after 256 bytes per call.

    Code: kernel/src/uart.rs. Test: same self-test. Shipped in 0.0.3 b1.

  • S3 Say so when there is no serial port S

    The boot prints [com1] no serial port found: screen and keyboard only, so the screen shows which case the machine is in.

    Code: kernel/src/main.rs. Shipped in 0.0.3 b1.

  • B1 Boot progress on the screen S

    Print a short marker before each step of the boot ([boot] heap, [boot] interrupts, ...). If the HP still stops, the last line names the step.

    Not needed now that the HP reaches its prompt; worth doing if a later driver hangs the boot.

  • B2 Keyboard controller: waits with a limit S

    keyboard::init emptied the PS/2 controller in a loop; a controller that is missing reads as "always full". The loop now stops after 256 bytes; the other waits in that file already had limits.

    Code: kernel/src/keyboard.rs. No test of its own: it needs a machine without the controller.

  • B3 IDE disk probe: give up when there is no controller S

    Checked: ata.rs already recognises an empty port address and limits every wait. Nothing to change.

    Seen working: the HP has no IDE disk and passes this step; so does QEMU's -machine q35.

Tier A: a usable prompt

  • A1 PS/2 keyboard on the real controller S

    Seen working on the HP: commands can be typed at the prompt.

    Which kind of keyboard (PS/2, or USB through the BIOS) was not noted. Under UEFI a USB keyboard will need U1 and U2.

  • A2 Framebuffer console M

    Draw text ourselves on the graphics framebuffer the bootloader hands over, with a built-in bitmap font. Unlocks UEFI boot (which has no text mode), more than 80x25 characters, and the DisplayPort outputs. No graphics-card driver is needed. Worked out in the display driver plan (phases G1 and G2). G1 and G2 are done in QEMU: the console draws its own text at 1920x1080 on QEMU's cards, and in the bootloader's graphics mode on any other card, under legacy BIOS and UEFI. Seen working on the HP (16 Nov 2026, b24): it boots to the desktop with the terminal window, and display shows the monitor's own resolution.

    Code: vga.rs, console.rs, boot.s (protected: Multiboot header). Test: the UEFI ISO boot gets a screen.

Tier B: storage

Until this tier is done the OS runs from a RAM disk on the HP: nothing survives a reboot.

  • D1 AHCI (SATA) driver L

    The machine's disks hang on an Intel AHCI controller. The driver finds every SATA disk on every AHCI controller, and BeeFS mounts from the first disk that holds it (IDE disks are still tried first). Polling, one sector per command. The rule stays: a disk that is not BeeFS is only read, never written; the boot says not BeeFS, left untouched.

    Code: kernel/src/ahci.rs (new), storage.rs. Tests: sata.scn (files and settings across reboots on an AHCI disk), a self-test for the command bytes and the disk's self-description, and a boot on QEMU's Q35 machine with a foreign disk (left bit for bit unchanged) next to a BeeFS disk. To confirm on the HP: the internal disk is listed and left untouched.

  • D4 Crash reports on a SATA disk S

    After a crash the kernel looks for the disk again to save its report, and only knows the IDE driver there. On a SATA disk the report is not saved.

    Protected: crash.rs.

  • D5 A/B kernel slots on a SATA disk M

    The slot code reads and patches the boot partition through the IDE driver only. Needed before a real machine can try a new kernel and roll back.

    Protected: bootslots.rs. Goes with D2 and D3.

  • D2 Where BeeFS lives on the real machine S

    A decision for the owner: a second partition on the USB stick (needs U3), or a partition on the internal disk (needs D1 and a safe way to create it).

    No code until decided.

  • D3 GPT partition tables M

    beefs/src/partition.rs now reads GPT next to MBR. A BeeFS partition has the type FE35CA6A-9309-4008-996D-254793C95A38; the first one on a disk is used. The table is only believed when both its checksums are right; a damaged one means "no BeeFS here", and the disk is left alone. Checked against a table made by sfdisk, and by booting QEMU with such a disk on the SATA controller. Not done: the backup table at the end of the disk is not used when the first one is damaged, and there is no boot scenario with a GPT disk yet (it needs a new option in the protected test runner).

    Test: host unit tests in beefs.

Tier C: network

  • N1 Intel I217-LM network card (e1000e family) L

    The HP's card (8086:153a). The e1000 driver now handles three families: the original e1000, the e1000e (82574L), and the cards built into the chipset (I217-LM and I217-V). For the chipset cards the start-up differs: a careful reset, the address from the registers the firmware filled in, no forced speed. net has a new chip: line with the link speed and, for the I217, the register values we need if the link does not come up. After the first try on the HP (link up, frames received, no DHCP answer) the start-up also applies the transmit settings these cards are documented to need, and net shows the card's own counters: how many frames it really put on the wire. Build b7 made it transmit on the HP (see the log above). Not done: the PHY workarounds other drivers carry (waking the PHY when the management firmware left it in its own mode); we add those only if the HP shows it needs them.

    Code: kernel/src/e1000.rs. Tests: net-e1000e-wire.scn (frames and both rings on a test wire) and net-e1000e.scn (DHCP, ping, a TCP transfer) on QEMU's e1000e; the I217 start-up path run by hand on that card (boot flag nic=chipset) to show it cannot hang. No emulator has an I217: the real test is the HP.

  • N2 Receive by interrupt M

    The card now raises its interrupt line when a frame arrives or the link changes, and the network thread looks at it at once. It is still polled every 10 ms as well, so nothing depends on the interrupt. It uses the old interrupt controller and the line the firmware gave the card; MSI comes with P1. A PCI line can be shared with a device we have no driver for: if the line keeps firing and the card says "not mine" 5000 times in a row, the line is switched off and the card is polled only. net has a new receive: line that says which of the two is in use. The boot flag net=poll switches the interrupt off.

    Works in QEMU on all three card families. To confirm on the HP: net should say receive: by interrupt (IRQ N, ... so far) with a count that goes up, and a ping from another machine should take under 1 ms instead of up to 10.

Tier D: USB

The largest block of work. Without it there is no keyboard under UEFI and no USB stick as a disk.

  • U1 xHCI host controller (USB 3) XL

    On this chipset it can drive all the USB ports. Memory-mapped registers, command and event rings, device slots.

    Needs P1 (or polling) and P3. Test: QEMU -device qemu-xhci.

    Works in QEMU (0.0.3, 16 Nov 2026), with polling: kernel/src/xhci.rs, command lsusb. It includes the handover from the firmware and the Intel register that moves the ports from the old USB 2 controller to xHCI, which the HP needs; neither can be tested in QEMU. Not tried on the HP yet. If it goes wrong there: the boot menu entry "without the USB driver" (usb=off).

  • U2 USB core and keyboard L

    Find devices, read their descriptors, hubs, and the keyboard protocol.

    Test: QEMU -device usb-kbd.

    Works in QEMU: devices on the machine's own ports are found and described, and a keyboard types (layouts, Shift, AltGr, key repeat). Not done: hubs. A keyboard plugged into a hub, or one with a hub inside, is listed by lsusb as not supported. Not tried on the HP yet; real keyboards are usually low-speed devices and QEMU's is not, so that path is untested.

  • U3 USB mass storage M

    Sticks and USB disks as block devices.

    Test: QEMU -device usb-storage.

  • U5 USB mouse M

    For the graphical desktop (desktop on): a pointer on the screen, and windows that can be picked and moved. A USB mouse speaks the same simple "boot protocol" family as the keyboard: a small report with the buttons and how far it moved, read from an interrupt endpoint. The window system (wm.rs) then needs a pointer drawn over the windows, and clicks sent to the window under it.

    Needs U1 and U2 (host controller, finding devices, reading descriptors); the mouse itself is the small part. Test: QEMU -device usb-mouse (or usb-tablet, which reports absolute positions), with the test moving the pointer through QEMU and a screenshot showing where it is.

    Works in QEMU: the pointer follows the mouse and the terminal window can be dragged by its title bar. Tablets (absolute positions) are not supported. Not tried on the HP yet.

  • U4 EHCI host controller (USB 2) L

    Only if xHCI turns out not to cover the ports we use.

Tier E: platform

Not drivers for one device, but what the drivers above stand on. Most of these touch protected files.

  • P1 APIC, I/O APIC and MSI L

    The modern interrupt controllers. Needed for MSI, which xHCI, AHCI and the network card prefer, and for more than one CPU core.

    Protected: interrupts.rs, interrupts.s.

  • P2 More memory M

    Map memory above 4 GiB, let the heap grow beyond 64 MiB, and add a page allocator for driver buffers.

    Protected: boot.s, allocator.rs.

  • P3 PCI: bridges, PCIe configuration space, capability lists M

    pci.rs already follows bridges, with the old port method. Done: the capability list (MSI, MSI-X, PCI Express, power management), shown by lspci -v. Still to do: the PCIe configuration space (registers above 255), when a driver needs it.

    Code: kernel/src/pci.rs.

  • P4 A better timer M

    HPET or the local APIC timer, and the CPU's own counter calibrated against it.

    Code: kernel/src/time.rs.

  • P5 ACPI on real firmware M

    Check power off, reset and the power button on the HP; real tables are larger and stranger than QEMU's.

    Protected: acpi.rs, power.rs.

  • P6 More than one CPU core XL

    Nothing needs it yet.

Tier F: nice to have

  • X1 Mouse (PS/2, later USB) M

    Nothing uses a mouse yet.

  • X2 Sound (Intel HD Audio) L

    No use for it yet.

  • X3 Intel HD Graphics driver XL

    Not needed: A2 uses the framebuffer the firmware set up. Phase G5 of the display driver plan says when that would change.

  • X4 NVMe disks M

    Not in this machine; useful for newer ones.

The host connection on real hardware

In the VM, beehive (AI, signals, deploys) talks to the OS over COM2. A real PC has at most one serial port and no host around it. So on the HP:

  • AI features and signals need the network path (the open N6 item "signals over the network"), which needs N1 first.
  • Deploying a new kernel means writing the stick again with tools/usbstick.py, until the kernel download (N6) and D2 exist.
  • The A/B slots and rollback need the boot disk layout on a real disk (D1, D2, D3).

Suggested order

  1. S1 to S3, B2, B3: reach the prompt on the HP (done). Write down what lspci shows.
  2. A1: type at the prompt.
  3. D1: a disk (done), then D2: decide where BeeFS lives.
  4. N1: network (done, works on the HP), which brings back the path to beehive.
  5. A2: framebuffer console, then UEFI boot.
  6. P1, P3, then U1 to U3: USB; then U5, the USB mouse for the desktop.
