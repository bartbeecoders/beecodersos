Making BeeCodersOs self-improving

A phased plan to turn BeeCodersOs into an OS that notices what it is missing, asks an AI to fix it, tests the change on itself and keeps it only when it works.

Plan v1 · 14 November 2026 · Starting point: BeeCodersOs 0.0.1, phases 1–3 done (kernel, BeeFS, BeeShell)

Next: phase 8, A/B kernels with automatic rollback.

1. The idea in one loop

"Self-improving" here means a closed loop that runs again and again, with every step automated and checked:

Observe→ Propose→ Build→ Test→ Deploy→ Verify→ Keep or roll back↺
  • Observe: the OS records crashes, slow paths, commands that don't exist yet and wishes typed by the user.
  • Propose: an LLM turns those signals into small, concrete code changes.
  • Build and test: the change is compiled and booted in a throwaway QEMU, where automated tests run against it.
  • Deploy and verify: the new kernel boots in a spare slot. If it doesn't come up healthy, the OS goes back to the last good kernel by itself.
Key principle: the AI is only as safe as the tests and the rollback. Phases 4 and 8 (tests and A/B boot) matter more than the AI parts. Without them, "self-improving" turns into "self-breaking".

2. Where we are, and what that means

What we have
  • 64-bit Rust kernel, ~4,200 lines
  • BeeFS on an ATA disk, with a host tool (beefs-tool)
  • BeeShell with history, layouts, file commands
  • Serial console (COM1) and ACPI power
  • /system/boot_count and boot.log
  • make iso, make run-vm, BeeFS unit tests
What we don't have yet
  • Version control (the project is not a repository)
  • Automated boot tests (pass/fail without a human)
  • Timer or clock, so no timestamps
  • Network stack, processes, user programs
  • Enough RAM or compute to run an LLM in the guest

Consequence: the LLM runs on the host at first. The OS talks to it over a serial link, which needs no network stack. Over time the boundary moves inward: the OS first reports, then asks, then requests changes, and finally installs and checks them itself.

3. Target architecture

Why a serial bridge instead of networking: COM2 (or virtio-serial later) is about 200 lines of driver code. It is easy to test and works in QEMU and libvirt today. The API key stays on the host, so the guest never holds secrets. A real TCP/IP stack can come later (phase 10) for real hardware.

4. Phases

Numbering continues from the README (phases 1–3 are done). Each phase ends with a clear test for "done".

Phase 4 — Safety net: version control and automated tests Done

An AI can't improve what can't be checked automatically, so this comes first.

  • Version control: put the project in git (or BeeGit) with a protected main. Every AI change becomes a branch and a reviewable diff.
  • Exit codes from QEMU: add QEMU's isa-debug-exit device and a kernel qemu_exit(code). A test run can then end with a pass/fail code instead of a window someone has to look at.
  • Kernel test mode: a selftest build/boot flag that runs in-kernel tests (allocator, BeeFS on RAM disk, keyboard decoder, ring buffer), prints results on serial and exits.
  • Shell scenario tests: a host-side runner (Rust or Python pexpect) that boots make run-serial, types commands and compares the output with expected text, for example mkdir a; cd a; pwd → /a.
  • make check: one command that runs unit tests, the selftest boot, the shell scenarios, a BIOS and a UEFI ISO boot, all with timeouts.
  • Agent instructions: a CLAUDE.md/AGENTS.md with the build commands, coding rules (no_std, no new dependencies without approval) and a list of protected files.
Done when: make check runs headless in under 2 minutes, returns 0 or non-zero, and catches a deliberately broken kernel.

Phase 5 — The OS observes itself Done

  • Time: PIT/HPET timer and RTC clock. This gives timestamps, plus date and uptime.
  • Structured event log: /system/log/events.jsonl on BeeFS, recording boot time, memory use, mount results, and the commands run with their exit status.
  • Crash records: the panic and exception handlers write a crash report (registers, message, build number) to a reserved area, which is saved to BeeFS on the next boot.
  • Missed-command log: every command not found is recorded. This is the best signal for what users expect the OS to do.
  • Shell commands: feedback "the ls output is hard to read" and wish "a text editor" write to /system/inbox/.
  • Host harvest: beefs-tool reads /system/log and /system/inbox from disk.img while the VM is off. This works before the bridge exists.
Done when: after a session in the VM, one host command prints a summary of the crashes, missed commands, wishes and boot-time trend.

Phase 6 — AI bridge: the OS can talk to an LLM Done

  • Guest side: a COM2 driver (reusing the 16550 code) and a small protocol of one JSON object per line: {"id":7,"type":"ask","text":"..."}. It gets replies with the same id, streamed in chunks, plus timeouts and a clear "AI offline" message.
  • Host side: the beehive daemon (Rust, using tokio) attaches to the VM's second serial port through a socket chardev in QEMU or libvirt. It calls the LLM, enforces token and cost budgets, and logs every exchange.
  • First AI features in the shell:
    • ask "how do I copy a folder?" answers using the OS's own help text and README as context.
    • explain explains the last error or crash report.
    • Missed-command suggestions: "dir not found, did you mean ls?"
  • Model choice: a fast, cheap model (Claude Haiku 5.5) for ask and triage, and a strong model (Claude Opus 5.5) for code changes. A local model through the same daemon is possible when working offline.
Done when: in virt-manager, ask answers within a few seconds, and stopping beehive leaves the OS fully usable.

Phase 7 — The improvement loop (host-driven, human-approved) Done

This is where the OS starts to improve itself. A host-side evolve pipeline:

  1. Triage: the LLM groups the harvested signals (crashes, missed commands, wishes) into a ranked backlog in Docs/backlog/, with one small item per file.
  2. Implement: a coding agent (Claude Code in headless mode, or the Agent SDK) takes the top item. It works in its own branch or worktree, must add or update tests, and keeps the diff small (for example, at most ~300 lines changed).
  3. Verify: make check must pass. Then the pipeline re-boots and replays the scenario that produced the signal. For example, if the user typed date, the test now expects a date.
  4. Review: you get a short report with the diff, test results, binary size and boot-time delta, and you approve or reject.
  5. Ship: merge, bump BUILD_NUMBER, make iso, make run-vm. The item is marked done and linked to the signal that caused it.

Crash reports go first: a reproducible panic plus a regression test is the safest kind of AI fix.

Done when: a wish typed in the VM (for example wish "uptime command") turns into a tested, merged feature, and the only human step is the approval click.

Phase 8 — Safe deployment inside the OS: A/B kernels and auto-rollback Next

  • Two kernel slots on the boot disk (/boot/kernel-a.elf, /boot/kernel-b.elf) and a Limine menu that boots the slot named in a small state file. This needs the kernel and Limine on the BeeFS disk, or on a small FAT boot partition next to it.
  • Trial boots: a new kernel gets e.g. 3 tries. The existing boot_count idea becomes a tries_left counter.
  • Health check: the kernel boots, runs a short selftest, mounts BeeFS and reaches the shell. Only then does it mark itself good. Otherwise the next boot falls back to the last good slot and files a crash report.
  • Data safety: kernels may only change the BeeFS on-disk format with a versioned migration that is tested on a copy of the disk first. Disks are still never auto-formatted.
Done when: deploying a kernel that panics at boot ends, without any human help, with the old kernel running and a crash report in the inbox.

Phase 9 — AI-written apps without touching the kernel Later

Most improvements don't need kernel changes. A sandbox lets the AI add features at low risk:

  • WASM runtime in the kernel (wasmi works in no_std). Programs are .wasm files in /apps, and the shell runs them like built-in commands.
  • Capability-based host API: print, read a line, read and write files under /home only, and time. Apps get no direct hardware access, so a buggy app can't crash the kernel.
  • Fast loop: the AI writes the app, it is compiled to WASM on the host, sent over the bridge into /apps, and is usable straight away with no reboot. Example apps: a text editor, grep, calc, small games.
  • This is also where more autonomy is safe: apps can be installed without approval, because removing one is just rm.
Done when: wish "a calculator" leads to a working calc command within minutes, without a reboot.

Phase 10 — The OS drives its own improvement Long term

  • improve command: the user describes a change inside the OS. The OS sends the request over the bridge, follows progress, receives the new kernel or app, installs it into slot B, reboots, checks itself and reports back.
  • Scheduled self-review: when idle, the OS sends its weekly statistics and asks for a backlog update.
  • Networking: a virtio-net driver plus smoltcp, so the bridge also works on real hardware. TLS is handled by the host or a proxy at first.
  • Running a model on the device: this is a long-term research goal. It needs paging, SMP, SIMD (AVX2) support and far more RAM. A tiny model (well under 1B parameters) could handle simple tasks like routing or completion. Real coding stays with a larger model elsewhere.

5. Autonomy levels and guardrails

Each kind of change gets the most autonomy its rollback story allows. A level only goes up after the one below has run cleanly for a while.

LevelWhat the AI may doApplies toApproval
L0 AdviseAnswer questions, explain errors, propose backlog itemsEverythingNone needed
L1 Auto-applyInstall or update WASM apps, docs, help text, tests/apps, Docs/, test filesAutomatic, logged, easy to undo
L2 GatedChange kernel code: shell, drivers, commandskernel/src (most files)Human approves the diff (later: automatic if tests and A/B health pass)
L3 ProtectedOnly propose; a human writes or approves each lineboot.s, interrupts, allocator, BeeFS on-disk format, acpi/power, the guardrails themselvesAlways human

Hard rules

  • The AI never changes its own judge: the test runner, make check, the guardrail config and this list are L3.
  • No secrets in the guest: API keys live only in beehive on the host.
  • Budgets: per-cycle and per-day limits on tokens, cost and number of attempts. After 3 failed attempts on an item, it goes back to a human.
  • Small steps: one backlog item per change, and diffs above a set size are rejected automatically.
  • Everything is traceable: each change links to the signal that caused it, the prompt, the model used, the test results and who approved it.
  • Kill switch: one setting (/system/ai = off, or stopping beehive) disables all AI actions. The OS must then still work normally.
  • User data is sacred: no automated change may delete or reformat anything outside /apps or a temporary directory.

6. How we know it is improving

"Self-improving" needs numbers that go the right way. The OS reports them through telemetry, and the pipeline tracks them per build:

MetricDirectionSource
Panics / exceptions per 100 boots↓Crash records
Missed-command rate (not found ÷ all commands)↓Shell log
Open wishes and their median time to delivery↓/system/inbox + backlog
Test count and make check pass rate↑Pipeline
Boot time to shell↓ (or stable)Event log
Kernel binary size and heap use at idleStableBuild + mem
AI change acceptance rate and rollbacksAcceptance ↑, rollbacks ↓Pipeline audit log
Cost per merged improvement↓beehive budget log

7. First steps

  1. Put the project under version control (git or BeeGit) and add CLAUDE.md with build and test rules.
  2. Add isa-debug-exit and a qemu_exit() function to the kernel.
  3. Write the first shell scenario test (boot, echo hi, expect hi, shutdown) and a make check target.
  4. Add the PIT timer and RTC, then date and uptime, the first timestamps.
  5. Log missed commands and add wish / feedback, written to /system/inbox.
  6. Add a beefs-tool summary command to harvest the logs on the host.
  7. Run the first improvement cycle by hand with Claude Code. Use it to shape the automated evolve pipeline.

Open questions for later: git or BeeGit as the source of truth · Claude API only, or a local model too · how much autonomy kernel changes get after A/B rollback works.
