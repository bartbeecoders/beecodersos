Beehive over the network

A plan to let BeeCodersOs reach beehive, the AI host, over the local network instead of a serial cable: so a real machine like the HP, which has no serial port, gets ask, explain, wishes and crash reports too.

Plan v1 · 16 November 2026 · Starting point: BeeCodersOs 0.0.3 b33 · the open item "signals over the network" of network phase N6.

Status: H1, H2 and H3 are built and work in QEMU (16 November 2026): beehive listens for paired machines, the OS connects with ai connect, and the link survives a beehive restart and a reboot. Not tried on the HP yet. H4 (a new kernel over the link) is not built: its design is in section 5 and needs three answers from you first. All six decisions below were taken as recommended.

1. Summary and recommendations

Today beehive connects to a VM's second serial port, which QEMU offers on the host as a local socket. Nothing leaves the host. A real machine has no such socket, so the link has to cross the network, and that changes one thing fundamentally: beehive gets a door on the LAN. Whoever can open it can spend your AI budget and put text into the improvement loop. Most of this plan is about that door.

shell: ask, wish, crash→ aibridge→ COM2 or TCP→ beehive→ LLM
Recommended choices
  • The OS connects out; beehive listens. The OS keeps its rule "nothing listens unless switched on", and a machine behind any router can reach the host.
  • Same messages as today. The JSON lines of the serial link (hello, ask, line, signal, ...) travel unchanged inside a TCP connection. The shell commands do not change at all.
  • Pairing with a key, proved without sending it. Each machine gets its own key from beehive, typed into the OS once. Both sides prove they know it with a keyed hash (HMAC-SHA-256), and every later message carries such a hash too, so nobody on the LAN can pretend to be the HP, pretend to be beehive, or change a message on the way.
  • Not encrypted. Questions and answers can be read by someone listening on your LAN, like the remote shell and the status page today. Real encryption needs TLS, which the network plan postponed. This is stated in the OS when the link is switched on.
  • Off by default on both sides. beehive only listens with --listen; the OS only connects after ai connect. The kill switch ai off closes the connection.
  • The serial link stays for VMs and the tests, exactly as it is.

Four phases, H1 to H4. H1 is on the host only, H2 is the OS side and works in QEMU, H3 makes it dependable and brings it to the HP. H4, downloading a new kernel over this link, is named but not planned here.

2. What we have and what is missing

Already there
  • The protocol: JSON lines, request ids, cancel, signals (kernel/src/aibridge.rs)
  • TCP client, DNS and DHCP in the OS, working on the HP
  • Threads, so a connection can be kept alive in the background
  • Random numbers (RDRAND) for keys and challenges
  • Signals are saved in /system/inbox first and sent when beehive is there
  • beehive: budget per day, logs, backends with every tool switched off
  • The pattern of the remote shell: a secret the OS keeps in /system, changes only from the local console
Missing
  • beehive can only connect to a local socket; it cannot listen
  • Any idea of which machine is talking: today it is "whoever is on that socket"
  • aibridge.rs is tied to COM2: bytes come from an interrupt, go out through the serial port
  • A hash function (SHA-256) in the OS
  • A place to save the key on the HP: it runs from a RAM disk (drivers todo D2, D3)
  • Commands to connect, and to see the state of the link

3. How it works

In the OS

  • aibridge.rs gets two ways out. Today it writes bytes to COM2 and reads them from a ring the serial interrupt fills. The network way uses the same ring for incoming bytes and a small bounded queue for outgoing lines. Everything above (request ids, timeouts, ask, explain, signals) stays as it is.
  • A hive thread owns the connection: it connects, does the proof (below), moves bytes between the socket and the two queues, and connects again when the link drops, waiting longer each time (2 s up to 1 minute). It never holds an FsGuard while waiting and fetches global state again after every wait, as the thread rules say.
  • Which link is used: the network one when ai connect was given, otherwise COM2 when the port exists. Never both at once: answers carry a request id, not a link.
  • Commands: ai connect HOST[:PORT] KEY (saved), ai disconnect, and ai shows the link: which kind, connected or why not, how long. Changing them works from the local console only, like the remote shell's settings.
  • Saved in /system/hive: host, port, the machine's name and its key.
  • Privacy: the event log records "hive connected" and "hive lost" with a reason, never the address or the key.

On the host

  • beehive.py pair NAME makes a key for one machine, stores it in beehive's state folder (readable by you only) and prints the line to type in the OS.
  • beehive.py --listen ADDRESS:PORT opens the door. Without it beehive behaves exactly as today. No default address: you name the LAN address, so it never listens on a network by accident.
  • beehive.py unpair NAME removes a key; beehive.py machines lists them with when each was last seen.
  • A network machine is served by the same code as a serial link (dispatch, the backends, the logs), so the rule "text from a VM never runs a command on the host" holds unchanged. Records in signals.jsonl get the machine's name where the serial ones have the socket.

4. Who may talk to beehive

The proof, once per connection. K is the machine's key; neither side ever sends it.

StepWhoMessageWhat it shows
1OS{"type":"hello","name":"hp","nonce":A,"version":..,"build":..}Which machine wants in. A is a fresh random number.
2beehive{"type":"challenge","nonce":B}Sent for unknown names too, so a stranger cannot find out which names exist.
3OS{"type":"auth","mac":HMAC(K, "os" A B)}The OS knows the key. Wrong: beehive closes the connection.
4beehive{"type":"welcome","mac":HMAC(K, "hive" B A),..}beehive knows the key too: the OS is not talking to an impostor.
5bothEvery later line carries "n" (a counter) and "mac", made with a key for this connection: HMAC(K, "session" A B).A line that was changed, repeated, or put in by someone else is dropped and the connection closed.

Because both random numbers go into every proof, a recording of an old connection is useless.

What this does and does not protect

Someone on your LAN wants to ...Result
use your AI budget, or send fake wishes and crash reportsStopped: no key, no service
learn the key by listeningStopped: the key is never sent
pretend to be beehive and feed the OS made-up answersStopped: step 4 and the signed lines
change a question or an answer on the wayStopped: the line's hash no longer fits
guess the keyStopped: 100 random bits; after 5 wrong tries from one address beehive ignores it for a minute
read your questions, the answers, wishes and crash reportsPossible. Not encrypted until TLS exists.
keep beehive busy with connectionsLimited: few connections at once, 10 s to finish the proof, short lines only before it
read the key from the machine's disk, having the machinePossible. Then: beehive.py unpair NAME.

Text from the OS stays what it is today: data. A paired machine can ask questions and file wishes; it cannot make beehive run anything, and the improvement loop treats wishes as requests a person approves.

5. Phases

Named H1–H4 (H for hive). Each ends with a test for "done". Sizes are rough estimates of new code.

H1 — beehive listens Done

  • pair, unpair, machines; keys in ~/.local/state/beehive/machines.json, mode 600.
  • --listen: accept, the proof of section 4, signed lines, then the existing dispatch.
  • Limits: 8 connections, 10 s for the proof, 8192 bytes per line (as in the OS), the wait after wrong tries, one connection per machine name (a new one replaces the old).
  • Budget: the daily limit stays one total; added is a limit per machine (default: the same number), so one machine cannot use up the day for all.
  • Logs: connections by machine name and outcome; never the key, never a proof.

About 250 lines in tools/beehive/beehive.py and its tests in tests/test_beehive.py. Both are protected. No change in the OS: nothing is visible to it yet.

Done when: a small test client (in the tests) pairs, asks the fake backend a question and files a signal; and the same client with a wrong key, a changed line, a repeated line, an oversized line or no proof at all gets nothing.

H2 — The OS connects Done

  • SHA-256 and HMAC in the beenet crate, with the published test values, so they are tested on the host first. Also there: building and checking the proof and the signed lines, with tests for cut-off and nonsense input.
  • aibridge.rs: the two ways out; the hive thread; the kill switch closes the connection and stops the thread from connecting.
  • ai connect, ai disconnect, the link's state in ai; settings in /system/hive; a warning when switching on that the link is not encrypted.
  • README: commands, the new files, how to pair.

About 600 lines including tests. Protected: the kill switch (ai off, /system/ai) is touched so that it also covers the network link; tests/boot_test.py gets a directive that starts a listening beehive.

Done when: in QEMU with its built-in network, ask is answered over TCP by the fake backend, a wish arrives in signals.jsonl under the machine's name, a wrong key gives a clear message in ai, and ai off ends the connection.

H3 — Dependable, and on the HP Done in QEMU, HP to try

  • Reconnect after beehive restarts, the cable is pulled, or the address changes (DHCP): wishes filed meanwhile wait in the inbox and are sent after the next connect. A short "still there?" message every 30 s notices a dead link.
  • An ask that was running when the link dropped ends with "the connection to the AI host was lost", not a two-minute wait.
  • The status page shows the link's state (connected or not; no address).
  • The HP: pair it and use it. Until BeeFS lives on a disk there (D2, D3), ai connect has to be typed again after every restart.

About 250 lines.

Done when: on the HP, ask gets an answer, a wish shows up in make report under the name "hp", and stopping and starting beehive needs no action on the HP.

How H1 to H3 went: built as planned, with these differences. A sealed line is written as MAC N JSON (hash and counter in front of the JSON text) instead of as fields inside the JSON: both sides then hash exactly the bytes that travel, with no question of how JSON is written out. ai connect takes the machine's name too (ai connect HOST[:PORT] NAME KEY) and tells at once whether it worked. beehive.py --connect none serves the network only. The command to connect waits up to five seconds for the outcome; a wrong key says "refused". Found on the way: the kernel's blocking network calls read the console's keys to notice Ctrl+C, also when a background thread made the call; a background thread no longer does. Not done: the link's state on the status page (httpd.rs is protected and the gain is small), and the trial on the HP.

H4 — A new kernel over the link Designed, not built: three answers needed

The network plan's "kernel download": the OS fetches a new kernel into the spare slot and tries it, with the A/B rollback as the net. Nothing in H1 to H3 lets the host push anything into the OS; H4 is the first thing that would. What looking at the code showed:

  • The kernel cannot write a kernel file today. By design it only rewrites two lines of limine.conf in place, "so the FAT file system never changes shape" (bootslots.rs). A deploy is done by the host with the VM switched off: tools/bootdisk.py rebuilds the whole FAT partition. H4 needs the kernel to write a file there for the first time.
  • The safest way to do that: bootdisk.py create gives each slot a file of fixed size (say 4 MiB, filled up with zeros), so the kernel only overwrites the contents of blocks that already belong to the file and changes nothing in the FAT. A kernel larger than the slot is refused. Existing boot disks (vm1) have to be made again once.
  • Checking what came in: beehive sends the kernel in pieces over the sealed link, then its SHA-256 and build number. The link already proves the sender has the pairing key; the kernel checks the hash of what it wrote before it marks the slot "pending". There is no signature of a person or a build machine: whoever has a machine's pairing key and beehive's place on the network can give that machine a kernel. A real signature needs public-key cryptography, which we do not have and should not write ourselves.
  • Who starts it: the OS asks (update, typed on its console), beehive only answers with what you put ready (beehive.py offer KERNEL). beehive can never start it.
  • Where it helps: only on a machine that boots from an A/B boot disk. That is vm1, which already has make deploy. The HP boots from the USB stick's ISO and has no slots, so H4 does nothing for it until the HP has a boot disk of its own (drivers todo D2, D3).

About 500 lines. Protected: bootslots.rs, tools/bootdisk.py, tools/deploy.py (unchanged, but its tests must keep passing), beehive. A mistake here can leave a machine that does not boot, which is why it is not built without your answers:

  1. Is "the pairing key vouches for the kernel" enough? It is as strong as today's make deploy, where whoever can write the disk image decides. The alternative is to wait for real signatures.
  2. May the boot disk's layout change (fixed-size slot files), with vm1's disk made again?
  3. Now, or after the HP has a boot disk? Until then H4 only repeats, over the network, what make deploy does for vm1.
Done when: a scenario on a boot disk fetches a kernel with update, boots it on trial, and it becomes the good slot; a kernel with a wrong hash, one that is too large, and a link that drops halfway each leave the good slot untouched; and a trial kernel that crashes rolls back as today.

7. Risks and guardrails

  • A door on the LAN. The largest change. Off unless --listen is given, with an address you name; only paired machines; limits before the proof. On a network you do not trust, do not switch it on.
  • Not encrypted. Said plainly in the OS and the README. Do not type secrets into ask.
  • Our own SHA-256. The network plan says "we should not write cryptography ourselves". A hash is the small, exactly specified part: about 80 lines, and any mistake shows in the published test values. Encryption and key exchange stay out. See the decisions.
  • A secret on the BeeFS disk. The rule is "no API keys or secrets on the BeeFS disk". The pairing key is the machine's own, like the remote shell's password that already lives in /system; it opens nothing but this machine's access to beehive and can be withdrawn on the host. Still an exception to the wording, so it is a decision.
  • The budget. A paired machine that goes wrong could ask in a loop. The per-machine limit caps it; the OS already allows one request at a time.
  • The deploy watchdog (tools/deploy.py, protected) reads health signals by build number. Signals from network machines have a name instead of a socket; the watchdog is not changed and keeps working for vm1 over serial.
  • Two links at once. Avoided by rule (network when configured, else serial), so answers cannot arrive on the wrong one.
  • Waiting. Connecting can take seconds. It happens in the hive thread, never in the shell: ask with no link answers "offline" at once, as today.
