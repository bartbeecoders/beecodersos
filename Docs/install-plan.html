1. Summary and recommendations

Today the HP boots from the USB stick and runs from a RAM disk: nothing survives a restart, not the settings, not the pairing with beehive, not a wish. An installation on its own disk fixes that, and gives the HP the A/B kernel slots with rollback that vm1 has.

boot the USB stick→ install→ choose the disk, confirm→ boot · os · data written→ remove the stick, restart
Recommended choices
  • The boot part is made on the development PC, not by the kernel. tools/bootdisk.py already builds a working boot area (bootloader for BIOS and UEFI, its settings, both kernel slots). The ISO carries that as one ready image and install copies it to the start of the disk. The kernel never has to build a FAT file system or know how the bootloader installs itself: far less that can go wrong.
  • Three partitions, each with a job (section 3): boot is replaced by an upgrade, os holds the system's own settings and logs, data holds your files and is never touched by an upgrade or a reinstall.
  • One command, three cases. On an empty disk: install. On a disk with BeeCodersOs: upgrade (new kernel into the spare slot, tried with rollback; os and data kept). On a disk with something else: refuse, unless you insist in a way that cannot happen by accident.
  • MBR partition table. It is what the boot disk tool makes and what was tested with rollback. Disks up to 2 TiB. GPT can follow.
  • In QEMU first, on throwaway disk images. The HP comes last, after the same build installed and upgraded itself in the tests.

2. What we have and what is missing

Already there
  • Disk drivers that read and write: IDE and SATA (AHCI, works on the HP)
  • BeeFS can format a partition (FileSystem::format)
  • The kernel reads MBR and GPT partition tables
  • tools/bootdisk.py: boot area with Limine and A/B slots; the kernel side of rollback (bootslots.rs)
  • The rule in storage.rs: a disk that is not BeeFS is "left untouched"
Missing
  • The files to install: the kernel cannot read the USB stick it booted from (no USB storage driver), and its own file is not kept in memory
  • Memory the bootloader hands over is reused by the kernel heap today, so files loaded with the kernel would be overwritten
  • Writing a partition table
  • More than one mounted file system (os and data)
  • Any command that changes a disk's layout, and the checks around it
  • A test that boots the ISO with a disk, installs, and boots the disk

Why the kernels are on "boot" and not on "os": the bootloader can only read FAT, so whatever it loads has to be there. That leaves "os" the role of the system's state. If you meant something else by an os partition, this is the place to say so (decision 2).

A fresh install leaves a note in /data/welcome.txt. The shell starts in /data.

4. How install works

  1. Building the ISO (on the PC): after the kernel is built, bootdisk.py makes a boot disk as it does for vm1, and the first 17 MiB of it (partition table, boot code, the FAT partition with both kernel slots) are cut off as install.img. The ISO's boot menu loads that file into memory next to the kernel ("module").
  2. At boot: the kernel notes where the bootloader put the image and keeps its heap away from it. Without the image (vm1, plain QEMU) install says it can only run from the install medium.
  3. install with no arguments lists the disks: size, model, what is on each (empty, BeeCodersOs with its version, or "something else: 3 partitions"), and what would happen. It changes nothing.
  4. install DISK shows the plan for that disk and asks for the confirmation of section 5. Then, in this order, so that a power cut at any moment leaves either the old state or a disk that says "install unfinished" and nothing half-valid:
    1. wipe the first sector (the disk is now "no partition table");
    2. write the boot image from sector 1 on;
    3. format os and data (BeeFS), write the welcome note;
    4. read back and compare what was written to the boot area;
    5. last, write the first sector: boot code and the table with the three partitions sized for this disk.
  5. Upgrade (the disk already holds BeeCodersOs): only the spare kernel slot is written, as make deploy does for vm1, and it is marked "on trial". After the restart the new kernel arms the rollback, checks itself, and becomes the good slot; if it fails, the old kernel boots again. os and data are not touched. If the boot area itself has to change (a newer bootloader), install DISK --reinstall writes boot and os again and keeps data.
  6. Afterwards it says: remove the stick and type reboot.

Booted from the installed disk, the kernel mounts os as / and data as /data. Booted from the stick with an installed disk present, it does the same, so an upgrade runs with your settings.

5. Not erasing the wrong disk

  • Nothing happens without a disk named on the command line, and never at boot or from a saved setting.
  • Only from the machine's own console: not from the remote shell, not through the AI bridge.
  • A disk with something else on it is refused with what was found. Overriding takes install DISK --erase and then typing a sentence that names the disk, for example erase 465 GiB WDC WD5000: the size and model it just showed you. A typo, or anything else, stops it.
  • An empty disk or a BeeCodersOs disk asks for a plain yes.
  • Never the disk the system is running from unless it is an upgrade.
  • A summary before the question: which disk, what is on it now, what will be erased, what will be kept.
  • In the tests it only ever runs on disk images made for the test.

The project rule says "never format or overwrite a disk that is not BeeFS". I read it as: nothing in the OS or the tests may do that by itself. A command you type, naming the disk, is your decision. That reading is yours to confirm (decision 3); if you disagree, --erase is left out and other systems must be removed with their own tools first.

6. Phases

I1 — The install image, and looking without touching Needs your approval

  • make iso builds install.img and puts it on the ISO; the boot menu loads it.
  • The kernel keeps the bootloader's modules: the heap starts above them (protected: allocator.rs, a few lines).
  • install lists disks and what would happen. No write code exists yet in this phase.

About 300 lines. Protected: allocator.rs, the Makefile (ISO rule), tests/boot_test.py (ISO boots with a disk attached). tools/bootdisk.py is used as it is.

Done when: the ISO boot in QEMU shows the image (size and the build inside it), its checksum matches the file on the PC after the heap has been used heavily, and install describes an empty disk, a BeeCodersOs disk and a foreign disk correctly.

I2 — A fresh install After I1

  • Writing the image, the partition table, formatting, comparing; the confirmations for empty and BeeCodersOs disks. Foreign disks are still always refused.
  • One BeeFS mounted for now: os. Data exists but is not mounted yet.

About 400 lines.

Done when: a scenario boots the ISO with an empty disk, installs, restarts without the ISO, and the installed system boots, keeps a file across a restart, and reports its A/B slots. Cutting the power in the middle (the test kills QEMU at each step) never leaves a disk that boots something broken.

I3 — os and data, upgrade, reinstall After I2

  • Two mounted file systems: os as /, data at /data; df shows both. (storage::FsGuard is protected: crash reports must keep working with two.)
  • Upgrade into the spare slot with rollback; --reinstall.

About 500 lines. Protected: storage::FsGuard, and bootslots.rs gets its first code that writes a kernel (inside an existing slot file only).

Done when: a scenario installs build N, boots a stick with build N+1, upgrades, and the disk boots N+1 with every file in / and /data intact; an upgrade to a kernel that crashes rolls back to N; a reinstall keeps /data.

I4 — The HP After I3

  • --erase with the typed sentence, if you allow it.
  • Install on the HP; boot it without the stick, in the boot mode you use.
Done when: the HP boots from its own disk, settings and the beehive pairing survive a restart, and an upgrade from a newer stick works.
