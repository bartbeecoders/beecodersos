A network stack for BeeCodersOs

A plan to connect BeeCodersOs to the local network and the internet: a network card driver, a small TCP/IP stack of our own, and a set of basic protocols that make it useful from the shell.

Plan v1 · 14 November 2026 · Starting point: BeeCodersOs 0.0.2 (phases 1–8 done).

Status: N1 to N5 and phase T (threads) are done. The OS finds its e1000 card, gets its address, gateway and DNS server automatically (DHCP) or by hand, answers and sends pings, resolves names, opens TCP connections (nc), fetches web pages over plain HTTP (wget), sets its clock (ntp) and copies files with TFTP (tftp). The protocols live in the beenet crate with host unit tests, including TCP over a simulated lossy link. TCP listening already exists in the stack (the tests needed it), but the OS accepts no incoming connections. The kernel runs cooperative threads: the network has its own, and a shell can run in a console session, which is the groundwork for a remote shell. N6 has started: the status page (httpd) and the remote shell (remote), both off by default, are done; signals over the network and the kernel download are open.

1. Summary and recommendations

Yes, TCP, but TCP sits on top of several smaller layers that have to exist first. The full path from the shell to the internet is:

PCI→ e1000 driver→ Ethernet + ARP→ IPv4 + ICMP→ UDP · DHCP · DNS→ TCP→ HTTP, NTP, …
Recommended choices
  • Network card: Intel e1000 first. vm1 already has one, it is QEMU's default, and it is well documented. A small device trait keeps the door open for virtio-net later.
  • Our own stack, in a separate crate beenet (no_std + alloc, like beefs). It fits the from-scratch project and the "no new crates" rule, and it can be unit-tested on the host with simulated packet loss. The alternative is the smoltcp crate (see decisions).
  • Plain-text protocols first, TLS later. We should not write cryptography ourselves. Until TLS exists, HTTPS-only sites are out of reach directly; plain HTTP, DNS, NTP, TFTP and anything on your LAN work.
  • Polling before interrupts. The 100 Hz timer already wakes the idle loop, so the stack can poll the card every 10 ms. That keeps the protected interrupt code untouched in the first phases.
  • Outbound only by default. Servers (web page, remote shell) come last and stay off until switched on.

Six phases, N1 to N6. After N3 the OS can ping names on the internet; after N4 it can fetch a web page over plain HTTP; N5 adds the commands that make it useful day to day; N6 adds servers and the links to the self-improvement loop.

2. What we have and what is missing

Already there
  • vm1: e1000 card on libvirt's NAT network (192.168.122.0/24, DHCP and DNS from dnsmasq, internet through NAT)
  • 100 Hz timer and clock: timeouts, retransmits
  • Memory identity-mapped up to 4 GiB: device memory and DMA buffers need no page-table work
  • Heap, lock-free IRQ queue, event log, shell with Ctrl+C handling
  • A pattern for a shared, host-tested crate (beefs)
  • Scenario tests in headless QEMU; QEMU has a built-in user-mode network that needs no root
Missing
  • PCI: finding devices, reading their addresses, enabling bus mastering
  • Any network card driver
  • Every protocol layer
  • A source of random numbers (TCP sequence numbers, DNS and DHCP IDs)
  • A socket-like API for shell commands
  • Processes or threads: everything runs in one flow, so network I/O must be cooperative

3. Architecture

How it runs without threads

BeeCodersOs has one flow of control. The stack is a state machine with one entry point, poll(now): it takes received frames from the card, updates ARP, answers pings, moves TCP connections forward and sends what is due (including retransmits). It is called from two places:

  • The idle loop (where the shell waits for a key; it already handles AI bridge messages there). So the OS answers pings and keeps its DHCP lease while you are at the prompt.
  • Inside blocking network calls, such as recv in wget, which loop on poll until data arrives, a timeout passes or you press Ctrl+C. This is the same pattern ask uses today.

A long-running command that never waits for input would starve the network; the socket calls and the idle loop cover every command that exists today. Servers in N6 need more than this: see Threads.

Why a separate crate

beenet never touches hardware: it gets frames in and gives frames out. That makes it testable on the host with cargo test: known packets with known checksums, two stacks wired back to back, and a simulated link that drops, duplicates and reorders packets to prove TCP recovers. The improvement loop's coding agent can then change network code and get a clear pass or fail, as with beefs.

5. Phases

Named N1–N6 so they don't collide with the roadmap's phase 9 (WebAssembly apps). Each ends with a test for "done". Sizes are rough estimates of new code.

N1 — PCI and the e1000 driver Done

  • PCI (kernel/src/pci.rs): configuration access through ports 0xCF8/0xCFC, scan bus 0, read vendor/device IDs, classes and BARs, enable memory access and bus mastering. lspci command.
  • e1000 (kernel/src/e1000.rs): reset, read the MAC address, set up receive and transmit descriptor rings in heap memory (physical address = virtual address here), send a frame, poll for received frames, link status.
  • NetDevice trait so the stack does not depend on the card.
  • Random numbers: RDRAND when the CPU has it, otherwise RDTSC mixed with the clock.
  • net shows the card, MAC, link state and frame counters.

About 600 lines. Touches no protected files: polling only, no interrupt changes.

Done when: in QEMU, net shows the MAC address QEMU assigned and "link up", and a test sees a broadcast frame from the OS in a packet capture.

Found while building it: under QEMU/KVM most e1000 register writes are buffered until the virtual CPU next exits to QEMU. An idle, polling OS never does, so the card stopped receiving after 31 frames. The driver now reads a register after updating the receive tail (a "write flush"). The test injects 80 frames while the OS idles to keep this fixed.

N2 — Ethernet, ARP, IPv4, ICMP: ping Done

  • Start the beenet crate: frame parsing and building, internet checksum, ARP with a cache, IPv4 send and receive with a routing decision (local subnet or gateway), ICMP echo.
  • poll wired into the idle loop and blocking calls.
  • net static … for a fixed address, ping, arp.
  • Host unit tests: checksums against known packets, ARP request and reply, two stacks pinging each other.

About 900 lines including tests.

Done when: the OS pings its gateway (10.0.2.2 in QEMU, 192.168.122.1 in vm1), and the host can ping vm1.

N3 — UDP, DHCP, DNS: automatic setup and names Done

  • UDP with a small socket table.
  • DHCP client: runs at boot when a card is found (does not delay the shell), renews the lease, falls back to "no address" cleanly. Settings saved in /system/net (dhcp, static … or off).
  • DNS resolver with a cache; nslookup; ping accepts names.
  • Boot line: [net] e1000 52:54:00:…, 192.168.122.57 (DHCP), gateway 192.168.122.1. Network events go to the event log.

About 800 lines including tests.

Done when: vm1 boots, gets an address by itself, and ping example.com works. That is the first packet to the internet and back.

N4 — TCP Done

The largest and most delicate part. Built and tested mostly on the host before it runs in the kernel.

  • Connection state machine (active open first, passive open for servers in N6), sequence numbers, acknowledgements, retransmission timer with backoff, receive window, FIN and RST handling, connection table, ephemeral ports.
  • Kept simple: out-of-order segments are dropped and re-requested, fixed-size buffers, a conservative send rate.
  • Socket API in the kernel: connect, send, recv, close with timeouts and Ctrl+C.
  • nc HOST PORT.
  • Host tests: two stacks connected by a simulated link with loss, duplication, reordering and delay must still transfer data intact and close cleanly.

About 1,500 lines including tests.

Done when: nc exchanges text with a server on the host, a 1 MiB transfer over a 10%-loss simulated link arrives intact in the unit tests, and a connection to a closed port fails quickly with a clear message.

N5 — Useful clients: HTTP, time, files Done

  • HTTP/1.1 client and wget, with output to the screen or a BeeFS file (within the 8 MiB file limit). GET only for now: POST is prepared in the request builder but has no command yet.
  • SNTP and ntp: the clock no longer depends on the VM's emulated clock.
  • TFTP client: move files between the OS and the host without stopping the VM.
  • ask could later use HTTP to reach an AI proxy on the LAN, so the AI bridge also works on real hardware without the COM2 port.

About 900 lines including tests.

Done when: wget http://example.com prints the page, ntp sets the clock to within a second, and a file round-trips through TFTP unchanged.

T — Cooperative threads (before N6) Done

Needed for servers, not for N1–N5. Details in section 6.

  • Kernel threads with their own stacks and a small context-switch routine.
  • Switches only at explicit points: waiting for a key, waiting on a socket, sleeping.
  • A background network task replaces the polling in the idle loop.

About 300–400 lines plus tests. No change to the interrupt code.

Done when: two shells (local and a test session) run side by side, a long-running command no longer stalls ping replies, and make check passes unchanged.

N6 — Servers and the self-improvement loop In progress

  • Done: TCP passive open (listen and accept), on top of cooperative threads (phase T).
  • Done: httpd: status page (version, uptime, slot state, threads, recent events) and read-only files from /public, for the LAN. Off by default.
  • Done: remote: a remote shell, Telnet style. Off by default, not encrypted, password always required and made up by the OS, one session, slow guessing, changes only from the local console.
  • Done: signals, and ask / explain, to beehive over TCP as an alternative to COM2: see the beehive link plan (H1 to H3).
  • Kernel download: fetch a new kernel into the spare A/B slot over HTTP or TFTP and try it, with the phase 8 rollback as the safety net. This is the roadmap's "the OS drives its own improvement" step, and it should wait for a signature check on the downloaded kernel.
  • Interrupt-driven receive, if polling every 10 ms proves too slow (needs approval: it touches the protected interrupt code).
Done when: a browser on your PC opens the OS's status page, and a deploy can be triggered without stopping the VM.

6. Threads

Decision: no threads for N1–N5; cooperative threads before N6; preemption only if an app ever needs it.

Why not first

The stack is a state machine with one poll() call, driven from the idle loop and from blocking calls. That is how small-system stacks are normally run, it covers every client-side phase, and it works unchanged once threads exist, so nothing is rewritten.

Preemptive threads would cost more than they give right now, because the kernel assumes one flow of control in several places:

  • Shared state (console, keyboard decoder, AI bridge, …) uses a "single flow only" wrapper with no locking.
  • The heap lock is a spinlock: on one core, a thread preempted while holding it deadlocks the next thread that allocates.
  • Crash reports check whether the file system was mid-operation, assuming only one thing can use the disk.
  • The interrupt entry code is protected, and a timer-driven context switch has to change it.

Mistakes there show up as rare, timing-dependent bugs, the kind automated tests are worst at catching. Multiple CPU cores are a further step again and buy nothing: nothing in the OS is CPU-bound.

Where threads become useful

  • Servers (N6): a remote shell next to the local shell is two flows of control; so is a web server that answers while you type.
  • Long-running commands: today a command that never waits for input stalls the network. TCP tolerates short stalls, because the other side retransmits, but not long ones.
  • Phase 9 apps: a running app should not freeze the shell.

The plan: cooperative threads

Cooperative (planned)Preemptive (not planned)
Switch happensOnly where a thread waits: for a key, a socket, a timer, or calls yieldAnywhere, on a timer interrupt
Existing "single flow" codeMostly still correct: nothing is interrupted halfwayNeeds locks everywhere, with interrupts disabled around them
Interrupt codeUnchangedMust be changed (protected)
A thread that never waitsBlocks the others; acceptable for kernel code we write and reviewIs cut off by the timer
Size300–400 lines + a context-switch routineSeveral times that, plus an audit of all shared state

Rules that keep it safe: a thread may not switch while it holds the file system (the existing guard already tracks that), each thread gets a fixed stack with a guard value that is checked on every switch, and the crash report records which thread was running.

Optional: the same threads could go in just before N4, which would make the socket API slightly cleaner. N4 does not need them.

7. Testing

  • Host unit tests for beenet (in make check): packet parsing and building against known bytes, checksums, the ARP cache, DHCP and DNS message handling, and the TCP state machine over a simulated bad link. Most bugs should be caught here, where they are easy to reproduce.
  • Kernel self-tests for the pieces that live in the kernel (PCI decoding, descriptor ring bookkeeping).
  • A test wire (@wire): the virtual card is connected to the test runner, which sees every frame the OS sends and can inject frames. Used from N1 for exact, repeatable driver and protocol tests.
  • Scenario tests in QEMU with a new @net directive that adds -netdev user and an e1000 card. QEMU's user-mode network needs no root and provides a DHCP server, a gateway at 10.0.2.2 that answers pings and reaches services on the host, a DNS forwarder, and a built-in TFTP server. The runner starts small Python servers on the host (HTTP, a TCP echo, a fake DNS) so tests never depend on the real internet.
  • Packet captures: QEMU can write every frame to a pcap file (-object filter-dump). Tests can assert on it, and you can open it in Wireshark when something looks wrong.
  • Real network: vm1 on libvirt's NAT network for manual checks against the internet. For other LAN machines to reach the OS (N6), the VM needs a bridged or macvtap interface instead of NAT.

8. Security and guardrails

  • Default deny inbound. Until N6 the OS answers ARP and ping and nothing else; unexpected TCP gets a reset, unexpected UDP is dropped. Servers are off until switched on, and the setting is saved on disk.
  • The remote shell is not encrypted. Password required, LAN use only, and the docs say so plainly. No remote shell is reachable in the default NAT setup anyway.
  • No secrets in the OS stays true: API keys remain in beehive on the host. Direct calls to AI services wait for TLS.
  • Untrusted input everywhere. Every packet is attacker-controlled data. The parsers get bounds checks on every field, tests with truncated and malformed packets, and fixed limits on table sizes (ARP entries, connections, DNS cache) so a flood can't exhaust the heap.
  • Random sequence numbers and IDs so connections and DNS answers can't be guessed.
  • Privacy rule extended: the event log records that a network command ran and whether it worked, not the hosts or URLs.
  • Protected list: the inbound defaults, the remote-shell password check and (later) the kernel-download signature check should join the files the coding agent may not change.
  • Kill switch: net off disables the card and is saved, like ai off.
