A display driver for BeeCodersOs

A plan to move the screen from 80x25 VGA text to a graphics framebuffer at up to 1920x1080, in virtual machines and on real hardware, with display drivers as interchangeable modules.

Plan v1 · 15 November 2026 · Starting point: BeeCodersOs 0.0.3 · covers items A2 and X3 of the drivers todo.

Status: G1 and G2 are done. The OS sets 1920x1080 itself on QEMU's cards, and on any other card it draws in the mode the bootloader set up. Seen working on the HP (16 November 2026, b24): it boots to the desktop and display shows the monitor's own resolution, so the firmware offers it and G5 (a driver of our own for the Intel card) is not needed. Since G1 there is also a desktop with a terminal window, on by default. G3 (a larger font, saved settings, write-combining) is done too; its speed still has to be measured on the HP with display test.

1. Summary and recommendations

A full HD screen does not need a driver for each graphics card. Almost every machine can hand the OS a linear framebuffer: a block of memory where each pixel is a few bytes. Who sets the resolution differs per machine, and that is the part we make modular:

shell, editor→ console→ screen (grid of characters)→ font renderer→ display driver→ pixels
Recommended choices
  • In VMs: a Bochs/QEMU display driver. QEMU's standard graphics card lets the OS pick any resolution with six register writes. This gives 1920x1080 in QEMU on day one, needs no protected file, and runs in every existing test.
  • On real hardware: the framebuffer the bootloader sets up. Limine asks the firmware for 1920x1080 (VBE in legacy BIOS boot, GOP in UEFI boot) and passes the result to the kernel. It works with any brand of graphics card. It needs a small change to the protected boot.s.
  • One driver interface, drivers tried in order. A driver that can set modes itself wins; then the bootloader's framebuffer; VGA text stays as the last resort. A boot flag display=text forces the old screen.
  • No native Intel driver now. Setting modes on the HP's HD Graphics 4600 ourselves is thousands of lines (clocks, DisplayPort link training). We do it only if the firmware cannot give 1080p (phase G5).
  • Text first. The goal of this plan is the existing console at a higher resolution, drawn with our own font. Drawing commands (pixels, lines, images) can come later on the same interface.

Five phases, G1 to G5. After G1 the OS runs at 1920x1080 in QEMU. After G2 it runs in graphics on the HP and under UEFI. G3 makes it fast and comfortable to read. G4 and G5 are optional extra drivers.

2. What we have and what is missing

Already there
  • vga.rs: 80x25 text at 0xB8000, hardware cursor, code page 437
  • console.rs: the only user of vga.rs; everything else prints through it (and through sessions for the remote shell)
  • Every character also goes to the serial port, which is what the tests read
  • pci.rs: finds devices, reads BARs
  • The first 4 GiB are mapped, so a framebuffer below 4 GiB can be written directly
  • Limine on the ISO and the A/B boot disk, with a resolution option
Missing
  • A font: in graphics mode nobody draws the letters for us
  • A screen size that is not fixed at 80x25 (console.rs uses vga::WIDTH)
  • A video-mode request in the Multiboot header, and reading the answer
  • Any way to choose a driver or a resolution
  • A screen under UEFI boot at all (UEFI has no text mode)
  • A test that looks at pixels

3. Architecture: modular drivers

The driver interface

One small trait in a new kernel/src/display.rs. A driver is a file plus one line in the driver list, the same pattern as NetDevice for network cards.

pub struct Mode { pub width: u32, pub height: u32, pub pitch: u32, pub format: PixelFormat }
pub enum PixelFormat { Xrgb8888, Xbgr8888, Rgb888, Rgb565 }   // from the firmware's color masks

pub trait DisplayDriver {
    fn name(&self) -> &'static str;
    fn mode(&self) -> Mode;
    fn framebuffer(&self) -> *mut u8;
    /// Drivers that cannot change the mode keep the default.
    fn set_mode(&mut self, _w: u32, _h: u32) -> Result<Mode, DisplayError> { Err(DisplayError::Fixed) }
    /// For cards that need to be told what changed (virtio-gpu). Others do nothing.
    fn flush(&mut self, _first_line: u32, _lines: u32) {}
}

/// Tried from top to bottom; the first that finds its hardware wins.
static DRIVERS: &[(&str, fn(&BootInfo, &[pci::Device]) -> Option<Box<dyn DisplayDriver>>)] = &[
    ("bochs",  bochs::probe),
    ("bootfb", bootfb::probe),
];   // nothing found: the VGA text screen, as today

Different graphics setups are then a matter of choice, not code:

  • Boot flags (read in bootargs.rs): display=bochs|bootfb|text forces a driver, mode=1920x1080 asks for a size.
  • A display command: shows driver, mode and pixel format; display mode 1280x720 changes it where the driver can; display test draws color bars. The choice is saved in /system/display, like /system/httpd.

Above the driver

  • Screen: what console.rs talks to. It has a size, a write position, colors, write_char, clear, a cursor and a scroll counter: exactly what vga::Writer offers today, minus the fixed 80x25. Two versions: the text screen (today's code) and the framebuffer screen.
  • Framebuffer screen (fbcon.rs): keeps every character cell in RAM (240x67 cells is 64 KB) and only draws cells that changed. It never reads from the framebuffer: reading video memory is very slow on real hardware. Scrolling moves the cells in RAM and redraws the differences.
  • Font (font.rs): a table of 8x16 bitmaps built into the kernel, covering the same characters as code page 437 so nothing that prints today changes. Double size (16x32) for readability on a large monitor.
  • Colors: the 16 vga::Color values stay as they are (so the protected interrupts.rs, which imports them, is not touched) and map to RGB through a table.

6. Phases

Named G1–G5. Each ends with a test for "done". Sizes are rough estimates of new code.

G1 — Display core, font, and full HD in QEMU Done

  • display.rs: the trait, the driver list, Mode, pixel formats, the display= and mode= boot flags.
  • bochs.rs: detect the card, check the video memory is large enough, set the mode, read it back.
  • font.rs and fbcon.rs: the framebuffer screen described above.
  • console.rs: use the screen interface and its real size; pick the framebuffer screen when a driver is found.
  • display command (show, mode, test), added to COMMANDS and the README.
  • The panic screen keeps working: it only uses console, and drawing a cell needs no heap and no lock.

About 800 lines plus the font table. Touches no protected file. Default mode in QEMU: 1920x1080; display=text gives the old screen.

Done when: make run opens a 1920x1080 window with a readable prompt, display prints bochs 1920x1080 in a scenario, the renderer self-tests pass, and make check is green. Checked on vm1 after a deploy.

How it went: built as planned, with these differences. The cells live in a fixed table (320x100 at most), not in the heap, so drawing works before and during a crash. What the text screen showed before the switch is copied over, so the first boot lines stay visible. display mode works but is not saved yet (G3). The driver also takes QXL, virtio-vga and VirtualBox cards: QXL was tried in QEMU and has its own scenario; vm1 itself has not been deployed to yet. The test runner got three directives: @screenshot WxH text|bars, plus @args (extra kernel flags) and @vga (the graphics card), which the display scenarios need.

G2 — The bootloader's framebuffer: the HP and UEFI Done

  • boot.s (protected): the Multiboot header asks for a 1920x1080x32 graphics mode.
  • bootfb.rs: read the framebuffer fields from the Multiboot info and check them before use: non-zero size, bytes per line large enough for the width, 16, 24 or 32 bits, whole area below 4 GiB, no overflow. Anything odd: text screen and a message.
  • limine.conf (ISO and boot disk): resolution: 1920x1080, and a second menu entry "BeeCodersOs (text mode)" with textmode: yes and display=text as the way back from a black screen. The menu gets a short timeout instead of 0.
  • A framebuffer above 4 GiB (possible on some UEFI machines): report it and stay on serial/text. Mapping it is a small follow-up if a real machine needs it.

About 250 lines. Protected: boot.s, tools/bootdisk.py. This closes A2 in the drivers todo.

How it went: boot.s got the nine header fields and nothing else. tools/bootdisk.py was not touched: the header already asks for 1920x1080, so no resolution: line is needed, and the boot disk has no text-mode entry (vm1 uses the bochs driver). Found on the way: the six color bytes in the Multiboot info sit at offset 112, two bytes later than the table in the Multiboot text says; bootloaders follow the C header. When the bootloader's mode cannot be used, the boot log now prints what was offered (size, bits, color layout), so a photo of the HP's screen or its serial log is enough to see why. With display=text in a graphics boot the kernel uses graphics anyway instead of leaving the screen black. Tested automatically by booting the ISO with a Cirrus card, which only the bootloader can set up: 1024x768 with 24 bits under BIOS, 800x600 with 32 bits under UEFI, each checked on a screenshot. The text-screen menu entry was tried by hand (BIOS: text screen; UEFI: graphics with a note).

Done when: the UEFI ISO boot shows the prompt on screen (today it shows nothing), the BIOS ISO boot with display=bootfb does too, and the HP boots from the USB stick into a graphics console and display reports its mode.

G3 — Fast and comfortable Done, HP to measure

  • Write-combining for the framebuffer memory. Without it every pixel write on real hardware goes to the card one by one, and a full-screen scroll at 1080p can take a noticeable fraction of a second. Done by marking the framebuffer's pages in the page tables (the tables are data set up by boot.s; the file itself is not changed).
  • Double-size font and display font 1|2; pick double automatically at 1080p and above.
  • Scroll in jumps when output arrives faster than the screen can draw (the serial log stays complete).
  • Save driver, mode and font size in /system/display.

About 300 lines. Whether write-combining is needed is measured on the HP first: display test prints how long a full redraw takes.

Done when: cat of a long file on the HP scrolls without visible stutter, and a full redraw at 1080p takes under 20 ms.

How it went: write-combining, the double font (display font 1|2|auto) and the saved settings (/system/display) are in. Differences from the plan: "auto" picks the double font only above full HD (1440 lines and more), because at 1920x1080 the small font gives a terminal of useful size and the choice is one command; the driver name is not saved, only mode and font. Write-combining changes the caching bits of the pages boot.s set up, from Rust, and can be switched off with the boot flag wc=off. Scrolling in jumps is not built: it waits for a measurement. Still to do on the HP: run display test and note the redraw time, and check display says video memory: write-combining.

G4 — virtio-gpu Optional

  • A virtio base layer (PCI capabilities, which pci.rs can already walk; queues), then the GPU device: create a 2D resource, attach our RAM as its backing, set the scanout, flush changed lines.
  • The first driver that needs flush, which proves the interface.

About 700 lines. Worth doing when a VM without a VGA card matters, or when virtio-net or virtio-blk are wanted too (they share the base layer).

Done when: a scenario boots with -vga none -device virtio-gpu-pci and display prints virtio-gpu 1920x1080.

G5 — Native Intel HD Graphics Only if needed

  • Step 1 (small): an intel driver that only reads the registers and reports what the firmware set up: which output, which mode, the monitor's EDID. Useful for diagnosis.
  • Step 2 (very large): set a mode ourselves: clocks, pipe, plane, DisplayPort link training over the AUX channel.

Step 2 is 2000+ lines, cannot be tested in QEMU (no emulated Intel graphics), and a mistake gives a black screen. X3 in the drivers todo stays "not planned" unless G2 shows the HP's firmware cannot reach 1920x1080 in either boot mode.

Done when: the HP shows 1920x1080 in legacy BIOS boot even though the firmware only offered less.

8. Risks and guardrails

  • Black screen on the HP. The screen is the only output there. Guardrails: the text-mode menu entry, display=text, and falling back to text whenever the bootloader's data fails a check. The framebuffer screen is switched on as early as the text screen is today, so boot messages are not lost.
  • A/B deploys. A kernel that boots but shows nothing still passes the deploy check (it answers on serial). The @screenshot check in the scenarios is what catches this before a deploy.
  • Data from the firmware is not trusted. Every size and address is checked before the first pixel is written, the same rule as for received network packets.
  • Crash reports. Drawing must work during a panic: no heap, no waiting, no lock that the crashed code may hold. The cell buffer is allocated once at start.
  • Threads. Drawing never waits, so no other thread runs in the middle of it; the rule "no Global::get() reference across a wait" holds automatically.
  • Speed on real hardware is unknown until measured (G3). In VMs it is not an issue.
  • Legacy BIOS mode list. The HP's firmware may not offer 1920x1080 through VBE. Then the choice is UEFI boot, or G5.
  • vm1 with QXL is expected to accept the Bochs registers but that is not verified. If not: switch its video model to vga (one line in the VM definition).
